# go-worker-pool

Конкурентная обработка списка URL на Go с использованием паттернов
Fan-out и Fan-in: ограниченный Worker Pool, каналы и `sync.WaitGroup`.

## Что показывает

- **Worker Pool** — фиксированное количество воркеров (`workerCount = 5`),
  а не горутина на каждое задание.
- **Fan-out** — несколько воркеров читают задания из одного канала `jobs`.
- **Fan-in** — все воркеры пишут результаты в один канал `results`,
  главная горутина собирает их.
- **Корректный порядок закрытия каналов** — `jobs` закрывается после
  отправки всех заданий, `results` — только после `wg.Wait()`,
  в отдельной горутине.
- **Отсутствие гонок данных** — взаимодействие горутин идёт только
  через каналы, проверено флагом `-race`.
- **Имитация разной скорости эндпоинтов** — задержка в `fetchURL`
  зависит от URL (хеш строки), а не только от случайности;
  поведение детерминировано для конкретного адреса.

## Запуск

```bash
go run main.go
```

Проверка на гонки данных:

```bash
go run -race main.go
```

## Пример вывода

```
=== Отчёт по обработке URL ===

[ 1] https://example.com            статус: обработан  время: 493ms    воркер: 1
[ 2] https://golang.org             статус: обработан  время: 294ms    воркер: 2
[ 3] https://github.com             статус: обработан  время: 302ms    воркер: 3
[ 4] https://stackoverflow.com      статус: обработан  время: 277ms    воркер: 4

=== Итоговая статистика ===
Всего обработано: 12
Успешно: 12
Среднее время обработки: 315ms
Суммарное время (последовательно): 3.785s
Фактическое время выполнения: 951ms
```

Разница между «суммарным временем» (сумма длительностей всех операций,
как если бы они шли последовательно) и «фактическим временем выполнения»
(реальный wall-clock от старта `main` до формирования отчёта) наглядно
показывает выигрыш от пяти параллельных воркеров.

## Буферизация каналов

В текущей версии буферы каналов `jobs` и `results` равны длине списка
URL. В продакшене размер буфера обычно ограничивают (например,
`2×workerCount`), чтобы производитель притормаживал при переполнении
очереди, а не резервировал память пропорционально всему набору данных.
