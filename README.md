# go-worker-pool

Конкурентная обработка списка URL на Go с использованием паттернов. Fan-out и Fan-in: ограниченный Worker Pool, каналы и `sync.WaitGroup`. Go 1.26, только стандартная библиотека.

## Что показывает

- **Worker Pool** — фиксированное количество воркеров (`workerCount = 5`), а не горутина на каждое задание.
- **Fan-out** — несколько воркеров читают задания из одного канала `jobs`.
- **Fan-in** — все воркеры пишут результаты в один канал `results`, главная горутина собирает их.
- **Корректный порядок закрытия каналов** — `jobs` закрывается после отправки всех заданий, `results` — только после `wg.Wait()`, в отдельной горутине.
- **Отсутствие гонок данных** — взаимодействие горутин идёт только через каналы, проверено флагом `-race`.
- **Имитация разной скорости эндпоинтов** — задержка в `fetchURL` зависит от URL (хеш строки), а не только от случайности; поведение детерминировано для конкретного адреса.

## Запуск

```bash
go run main.go
```

Проверка на гонки данных:

```bash
go run -race main.go
```

Время и номер воркера для одной и той же строки могут отличаться от запуска к запуску: длительность детерминирована для URL, но порядок распределения задач между воркерами — нет.

## Буферизация каналов

В текущей версии буферы каналов `jobs` и `results` равны длине списка URL. В продакшене размер буфера обычно ограничивают (например, `2×workerCount`), чтобы производитель притормаживал при переполнении очереди, а не резервировал память пропорционально всему набору данных.
